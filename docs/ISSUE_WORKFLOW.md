# Issue・PRの残件運用

Issueを一つの実装で最後まで完了できないことは許容する。ただし、途中まで実装した状態を元IssueのコメントやPR本文だけで管理し続けない。実装可能な残件は、独立したIssueとして登録し、PRとIssueを相互にたどれる状態にする。

## 設計書への反映

設計の正本は `docs/IMPLEMENTATION_PLAN.md` とし、検討中の案ではなく、確定した現在の仕様だけを記載する。

- Issueは、目的・設計案・受入条件を議論し、仕様を確定する場所とする。Issueを作成しただけでは設計書の更新対象にしない。
- Issue本文で明示的に「確定仕様」とされ、意思決定が完了している内容は、実装前でも設計書へ反映してよい。
- 通常は、実装PRをマージするまでに設計書との整合を確認する。実装によって設計が追加・変更・置換された場合は、原則としてそのPR自身で `docs/IMPLEMENTATION_PLAN.md` も更新する。
- PRでは設計への影響を「なし」または「あり（設計書更新済み）」として明示する。設計への影響があるのに設計書を更新しない場合は、その理由と確定前であることを明記する。
- 実装中に当初のIssue案から仕様が変わった場合は、会話やPRコメントだけを正本にせず、最終的な受入条件と設計書を実装結果に合わせる。
- 未マージPRの暫定実装、実験結果、会話だけで合意した案は、それだけを根拠に確定仕様として設計書へ入れない。merged PR、Issueの確定仕様、現行実装を総合して判断する。
- 設計書には過去の検討経緯や候補案を重複して残さず、現在有効な仕様を優先する。置き換えられた仕様は、必要な互換性・移行情報を除き、現行仕様と誤認しない形に整理する。

役割は次のように分ける。

- Issue：設計を議論・確定する場所
- PR：実装と設計書を一致させる場所
- `docs/IMPLEMENTATION_PLAN.md`：確定後の現在形を保持する正本

## 部分実装をマージする前

1. 元Issueの受入条件を一つずつ確認し、「今回完了する条件」と「未完了の条件」を分ける。
2. 未完了の作業が独立して実装できるなら、別Issueに切り出す。Issueには目的、対象範囲、受入条件、依存関係、今回のPRから引き継ぐ内容を記載する。
3. 残件Issueを作成したら、元Issueと実装PRの両方からリンクする。元Issueには「残件」、残件Issueには「元Issue」「先行PR」を記載する。
4. 残件Issueを作成したら、その本文に独立した行で `Parent: #<元Issue番号>` を記載する。元Issueの残件はこのIssueへ移管したものとして、元Issueはクローズする。残件Issueなしに部分PRだけをマージして元Issueを閉じてはならない。

残件が単なる追加改善で、元Issueの受入条件をすべて満たしている場合は、元Issueを完了にしてよい。その場合も、追加改善のIssueを作成し、元Issueから後続作業としてリンクする。

## PR本文の書き分け

- `Closes #123`、`Fixes #123`、`Resolves #123`：このPRを対象ブランチへマージすれば、Issueの受入条件がすべて満たされる場合だけ使う。
- `Refs #123`：Issueの一部だけを実装する場合、調査・準備だけの場合、または関連するだけの場合に使う。
- 一つのPRで複数のIssueを扱う場合は、完了するIssueと参照するIssueを分けて列挙する。曖昧な「関連Issue」だけで済ませない。

Draft PRの段階で完了条件が確定していなければ`Refs`にしておき、受入条件と検証結果を確認した後に、必要な場合だけ`Closes`へ変更する。

## クローズ時の確認

PRをマージする前に、次を確認する。

- PRの差分が完了対象Issueの受入条件を満たしている。
- 未完了の条件が残る場合、その条件に対応する残件Issueが存在する。
- 残件Issueに、元Issueと今回のPRへのリンクがある。
- 元Issueを閉じる場合、完了PRなら`Closes`等、残件移管なら残件Issue本文の`Parent: #<番号>`が存在する。
- 実装済み、CI確認済み、実機受入済みを混同していない。
- 設計への影響がある場合、`docs/IMPLEMENTATION_PLAN.md` が確定した実装・仕様と一致している。

PRマージ後は、GitHub上で次の状態を実際に確認する。

- 完了対象のIssueだけがクローズされている。
- 残件Issueはopenのまま引き継がれ、元Issueはクローズされている。
- 元Issue、残件Issue、PRを相互に開ける。
- Projectの表示がIssue・PRの実態と一致している。`status:*`ラベルは使用しない。

Projectの更新に失敗した場合は[Project自動同期](PROJECT_AUTOMATION.md)の復旧手順で再実行する。Project表示だけをIssue完了の根拠にしない。受入条件が残る場合は、残件Issueを作成してから元Issueを閉じる。

## Issueを分割するときの判断

残件Issueは、担当者が一回の作業で受入確認まで進められる大きさにする。単なる作業メモや「あとで確認」だけのIssueは作らない。一方で、複数の独立した受入条件を一つのIssueに詰め込み、部分実装のたびに状態が曖昧になる構成も避ける。

元Issueを閉じて残件Issueへ移管する場合、残件Issue本文に次を明記する。

- `Parent: #<元Issue番号>`
- 引き継いだ条件、対象範囲、先行PR

残件Issueは独立した完了単位として扱う。元IssueはProject上もDoneにして履歴の入口として残し、残件Issueを完了したらそのIssue自身を閉じる。
