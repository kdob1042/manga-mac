# Issue・PRの残件運用

着手・Project状態・障害復旧は[PROJECT_AUTOMATION](PROJECT_AUTOMATION.md)、ブランチとCIは[DEVELOPMENT](DEVELOPMENT.md)を参照する。本書は仕様確定と部分完了を扱う。

## 仕様を確定する

| 場所 | 役割 |
| --- | --- |
| Issue | 目的・案・受入条件を議論し、確定する |
| 実装PR | 最終的な受入条件・実装・設計書を一致させる |
| [IMPLEMENTATION_PLAN](IMPLEMENTATION_PLAN.md) | 確定した現在の仕様を保持する |
| [VALIDATION](VALIDATION.md) | 実施した検証と未実施条件を残す |

- Issue作成だけでは設計書を更新しない。Issueで「確定仕様」と明記した内容は実装前でも反映できる。
- 設計の追加・変更・置換は原則その実装PRで設計書も更新する。PR本文に「設計への影響: なし / あり（更新済み）」を明記する。未更新なら理由と確定前であることを記す。
- 未マージの暫定実装・実験・会話だけで仕様を確定しない。merged PR、Issueの確定仕様、現行実装で判断し、途中で変わった受入条件も更新する。
- 置換済みの案は現在の仕様と混在させない。互換性・移行条件は残し、検討経緯はIssue、検証履歴はVALIDATIONで追えるようにする。

## 部分完了を引き継ぐ

1. PR本文に独立した行で `Refs #123`。全受入条件を満たした場合だけ `Closes #123`（`Fixes` / `Resolves`も可）とする。複数Issueは一行ずつ記す。
2. 部分実装はマージ前に残件Issueを作る。目的・範囲・受入条件・依存・先行PRを記し、本文に独立した `Parent: #元Issue番号` を置く。元Issue / PRにも相互リンクする。
3. マージ前は受入条件と設計書、マージ後は元Issue・残件・PRの実状態を確認する。残件をコメントやPR本文だけに残さず、独立して受入できる単位にする。

残件Issueなしで元Issueを閉じない。追加改善だけなら元Issueは完了でよいが、未検証の必須条件を追加改善に言い換えない。実装・CI・実機受入を区別し、Project表示だけを完了根拠にしない。自動クローズ条件と同期失敗時の対応はPROJECT_AUTOMATIONを正本とする。
